# AGENTS.md

1. Любую задачу начинай с чтения `docs/game_overview.md`. Если в постановке задачи есть расхождения с `docs/game_overview.md` — спрашивай, нужно ли доработать `docs/game_overview.md` в соответствии с новыми данными или пользователь ошибся, и тогда нужно скорректировать постановку задачи в соответствии с `docs/game_overview.md`.
2. При составлении плана всегда делай это с расчетом на то, что план составляется для джуниор-разработчика, которому нужно подробно объяснить все шаги и критерии успешности.
3. Если `cargo` не найден в `PATH` — используй `C:\Users\andreybotanic\.cargo\bin\cargo.exe`.
   - Для штатной очистки `target` используй `cargo clean-target` — эта команда удаляет мусор, но сохраняет cargo-кэш сборки.
   - Для редкой глубокой зачистки с потерей build cache используй `cargo clean-target-hard`.
   - Для релизной сборки после очистки используй `cargo build-release`.
4. Крупные изменения обязательно должны иметь тесты.
   - Запускай тесты только по тем модулям, которые реально изменялись, либо напрямую связаны с изменяемым кодом.
   - Не запускай несвязанные тесты только "на всякий случай": например, при изменениях UI не нужно запускать тесты на физику труб, если эти изменения не затрагивают pipe-runtime и его контракты.
5. Правила ведения документации:
   - в `docs/game_overview.md` фиксируется только информация по игровому процессу и пользовательским механикам;
   - вся внутренняя техническая информация (архитектура, инженерные детали, ограничения реализации, технические решения) фиксируется в `docs/technical_overview.md`;
   - важные изменения проекта фиксируются в `docs/CHANGELOG.md` кратко и по существу, без мелкого технического шума.
   - зона ответственности файлов ведётся централизованно в `docs/project_structure.md` с кратким описанием каждого файла репозитория;
   - при добавлении, удалении, переименовании файла или изменении его роли обязательно обновляй `docs/project_structure.md`.
   - все файлы `*.md` должны храниться в кодировке `UTF-8 with BOM`; при создании и редактировании markdown-файлов сохраняй этот стандарт.
6. Любой крупный и самостоятельный блок кода должен быть оформлен как отдельный файл/модуль. Особенно это касается кода, который потенциально может переиспользоваться (например, поля ввода, панели и другие UI-блоки).
7. Код нужно документировать. Минимальный уровень документирования:
   - для всех `pub struct` и `pub fn` обязателен `Rustdoc`-комментарий в формате `///` прямо перед объявлением;
   - комментарий должен кратко объяснять назначение сущности (1-3 строки), без пересказа очевидного;
   - для сложной внутренней (private) логики допускаются точечные `//` комментарии.
8. После завершения любой задачи:
   - обновляй документацию по правилам выше (gameplay в `docs/game_overview.md`, техчасть в `docs/technical_overview.md`, важные изменения в `docs/CHANGELOG.md`);
   - перед релизной сборкой обязательно очищай мусор в `target`: используй `cargo clean-target` или сразу `cargo build-release`;
   - для финальной проверочной релизной сборки предпочитай `cargo build-release` (эта команда сама сначала удаляет мусор в `target`, но сохраняет cargo-кэш сборки, а затем выполняет `cargo build --release`);
   - `cargo clean-target-hard` используй только когда нужно разово освободить много места и допустима следующая «холодная» пересборка зависимостей;
   - запускай релизную версию и проверяй логи — приложение должно запускаться, а в логах не должно быть ошибок; не забывай закрывать запущенное приложение.
9. Правило CPU/GPU симуляции газа:
   - CPU-реализация (`Rust`) является единственным эталоном алгоритма;
   - GPU-реализация (`WGSL`) обязана быть прямым переносом CPU-алгоритма без самостоятельных алгоритмических отличий;
   - любое изменение логики CPU-симуляции газа должно в том же изменении сопровождаться эквивалентным изменением WGSL;
   - изменения считаются незавершенными, пока не добавлены/обновлены тесты CPU↔GPU parity и они не проходят.
10. Если требуется сгенерировать спрайты или другие картинки:
   - для генерации изображений используй навык `imagegen`;
   - спрайты для всех клеток/структур должны иметь размеры кратные 64, минимальный размер спрайта 64*64 пиксела;
   - спрайты должны быть в формате PNG с прозрачностью;
   - при генерации спрайтов клеток/структур всегда нужно генерировать пару спрайтов (если явно не сказано иное): обычный и "силуэт" - только белый контур на прозрачном фоне;
   - при генерации спрайтов придерживайся стилистики: мультяшное, яркое, минималистичное, с четкими границами;
11. Если не было изменений в коде (например были только правки документации или спрайтов), то тесты запускать не нужно.
12. Размер файлов с кодом нужно стараться держать не более 500 строк. Если файл получается более 500 строк, то нужно попробовать разбить его на отдельные компоненты/модули. При этом если код файла сильно связан и не может быть разбит на отделные части, то файл можно оставить как есть.
13. При изменении физики газа в трубах сначала запускай слабые (`smoke`) версии pipe-тестов, и только если они прошли — запускай полные долгие сценарии.
14. При работе над крупными задачами не останавливайся на пол пути. План обязательно нужно довести до самого конца, чтобы задача была выполнена. Остановиться, не выполнив задачу полностью, можно только в одном случае: возникла техническая невозможность реализовать намеченный план. Запрещено останавливаться на пол пути, если нет никаких реальных блокеров.
15. Если какая-то фича добавляется плагином (например через default_plugin), то ядро в большинстве случаев вообще не должно знать про существование этой фичи. Любой контент, любая логика, пришедшие из плагина, должны жить только в плагине. Всё взаимодействие этой логики с ядром должно быть только (ТОЛЬКО И ЕЩЕ РАЗ ТОЛЬКО) через SDK.
